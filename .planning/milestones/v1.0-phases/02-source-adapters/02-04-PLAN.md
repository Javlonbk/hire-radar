Create `src/adapters/telegram.ts` exporting:
```typescript
export interface TelegramOptions {
  channel: string;
  apiId?: number;
  apiHash?: string;
  session?: string;
  clientFactory?: (apiId: number, apiHash: string, session: string) => TelegramLike; // injectable for tests
  sleep?: (ms: number) => Promise<void>;   // injectable; default real
  jitterMs?: () => number;                  // default: 2000 + random*3000 (2–5s)
}
export interface TelegramLike {
  connect(): Promise<void>;
  isUserAuthorized(): Promise<boolean>;
  getMessages(channel: string, opts: { limit: number; minId?: number }): Promise<Array<{ id: number; message?: string; date: number }>>;
}
export function createTelegramAdapter(opts: TelegramOptions): SourceAdapter
```

`id = "telegram:" + opts.channel`.

`fetch(since: Date)`:
1. If `!opts.apiId || !opts.apiHash || !opts.session`, throw `new Error("Telegram session missing for " + opts.channel + " — run `hire-radar auth` to authenticate")` (never embed the session value). Do NOT log opts.session anywhere.
2. Build the client: `const client = (opts.clientFactory ?? defaultFactory)(opts.apiId, opts.apiHash, opts.session)`. `await client.connect()`.
3. `if (!(await client.isUserAuthorized())) throw new Error("Telegram session expired for " + opts.channel + " — run `hire-radar auth` to re-authenticate")` (Pitfall 1 — stale session returns silently otherwise).
4. `await sleep(jitterMs())` before the read (Pitfall 3 — inter-channel pacing; sequential by construction since adapters run sequentially in the orchestrator).
5. Read with FloodWait retry:
```
async function read(): Promise<msgs> {
  try { return await client.getMessages(channel, { limit: 100 }); }
  catch (e) { if (e instanceof FloodWaitError) { await sleep(e.seconds * 1150); return await client.getMessages(channel, { limit: 100 }); } throw e; }
}
```
6. Filter messages: keep `m.message` non-empty AND `m.date * 1000 >= since.getTime()`. Map each to RawItem: `sourceId: id`, `nativeId: String(m.id)`, `rawText: m.message`, `rawJson: { id: m.id, date: m.date }`, `fetchedAt: new Date()`, `contentHash: contentHash(id + ":" + m.id)`.
7. Return the RawItem[].

`defaultFactory` constructs `new TelegramClient(new StringSession(session), apiId, apiHash, { connectionRetries: 3, floodSleepThreshold: 300 })` (floodSleepThreshold per Pitfall 2). Default `sleep = ms => new Promise(r => setTimeout(r, ms))`, `jitterMs = () => 2000 + Math.floor(Math.random()*3000)`.

Tests inject `clientFactory` returning a `TelegramLike` stub:
  - (a) authorized stub returning 2 messages (one before `since`, one after) → assert only the newer becomes a RawItem with correct contentHash;
  - (b) stub whose `isUserAuthorized` resolves false → assert fetch rejects with a message containing "hire-radar auth" and that opts.session does NOT appear in the error message;
  - (c) `createTelegramAdapter({ channel, ... no session })` → fetch rejects with the actionable missing-session message;
  - (d) stub whose first getMessages throws `new FloodWaitError({ seconds: 3, ... })` then succeeds → assert sleep was called with 3*1150 and messages returned (injected no-op sleep records the arg).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| TELEGRAM_SESSION / api creds (env) → adapter | Personal-account credentials; full account takeover if leaked |
| Telegram MTProto channel content → RawItem | Untrusted message text crosses into SQLite |
| FloodWait / spam-filter signal → adapter | Telegram-side throttling controls request pacing (ban risk on abuse) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10 | Information Disclosure | session/credential handling | mitigate | Session + api_hash read from env only (config.ts), never logged and never embedded in thrown errors; error messages reference the channel + `hire-radar auth`, not the secret value |
| T-02-11 | Spoofing/Repudiation | stale session silent reads | mitigate | isUserAuthorized() checked before any read; false → throw actionable error instead of returning silent empty results (Pitfall 1) |
| T-02-12 | Denial of Service | FloodWait / aggressive reads → account ban | mitigate | FloodWaitError caught + retried with `seconds * 1.15` buffer, floodSleepThreshold=300, 2–5s inter-channel jitter, sequential reads only, min-id/since watermark so unchanged channels re-fetch nothing (Pitfalls 2, 3, 12) |
</threat_model>
