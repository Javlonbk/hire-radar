# Roadmap: Hire Radar

## Overview

Four phases take hire-radar from an empty repo to a working ingestion CLI. Phase 1 lays the SQLite schema, config, and hash utilities that every other layer depends on. Phase 2 builds all three source adapters (hh.uz, RSS, Telegram) with the orchestrator that runs them in isolation. Phase 3 wires in the Claude Haiku extraction pipeline with caching and dedup. Phase 4 delivers the three user-facing CLI commands and the distributable binary.

## Phase Details

### Phase 1: Foundation
**Goal**: The database, config, and hash utilities exist and are correct so every other layer can build on them
**Depends on**: Nothing (first phase)
**Requirements**: FNDN-01, FNDN-02, FNDN-03
**Success Criteria** (what must be TRUE):
  1. Running the project initializes a SQLite file with the correct 4-table schema (sources, raw_items, extraction_cache, vacancies) in WAL mode
  2. User can supply Telegram credentials, channel whitelist, hh.uz filters, RSS URLs, and Anthropic API key via config file or env vars without touching source code; missing required values produce an actionable error
  3. Identical Uzbek text variants (uz-Latn vs uz-Cyrl homoglyphs, mixed case) produce the same SHA-256 content hash
**Plans**: 3 plans
- [x] 01-01-PLAN.md — Project bootstrap: ESM package.json, strict tsconfig, vitest, .gitignore, config.example.json, src/ skeleton
- [x] 01-02-PLAN.md — SQLite layer: 4-table schema.sql, WAL + busy_timeout client, synchronous transaction helper
- [x] 01-03-PLAN.md — Utilities: normalize + SHA-256 content hash (homoglyph fold) and Zod-validated env/file config loader

### Phase 2: Source Adapters
**Goal**: Users can ingest raw job posts from hh.uz, RSS feeds, and Telegram channels into SQLite, with each source failing independently
**Depends on**: Phase 1
**Requirements**: SRCE-01, SRCE-02, SRCE-03, SRCE-04, SRCE-05
**Success Criteria** (what must be TRUE):
  1. Running ingest fetches new hh.uz postings since the last run using a date cursor; subsequent runs fetch only new items
  2. Running ingest fetches RSS items with conditional GET (ETag/If-Modified-Since); non-UTF-8 feeds (windows-1251) are decoded correctly
  3. Running ingest fetches new Telegram posts from whitelisted channels since the last message-id watermark, with FloodWait retry and per-channel jitter
  4. A network failure or API error on one source prints that source's error and continues fetching from the remaining sources
  5. Raw items are written to SQLite before extraction is attempted; a crash mid-run leaves already-fetched raws intact for the next run
**Plans**: 4 plans
- [x] 02-01-PLAN.md — Adapter contract (SourceAdapter/RawItem) + hh.uz REST adapter + raw-items/cursor DB helpers
- [x] 02-02-PLAN.md — RSS adapter: conditional GET, windows-1251 transcode, SSRF scheme guard
- [x] 02-03-PLAN.md — Orchestrator + registry: sequential fault isolation, persist-before-cursor, 7-day backfill / --since
- [x] 02-04-PLAN.md — Telegram gramjs adapter (auth gate, min_id watermark, FloodWait, jitter) + registry wiring

### Phase 3: AI Extraction Pipeline
**Goal**: Raw posts are automatically converted to structured, deduplicated vacancies in SQLite using Claude Haiku, with API calls gated by a content-hash cache
**Depends on**: Phase 2
**Requirements**: EXTR-01, EXTR-02, EXTR-03, EXTR-04
**Success Criteria** (what must be TRUE):
  1. Running ingest on a batch of raw posts produces structured vacancies with title, company, skills, salary, location, remote type, apply contact, and language correctly populated for posts in uz-Latn, uz-Cyrl, Russian, and English
  2. A raw post containing multiple job listings produces multiple vacancy rows; a non-job post (announcement, meme) produces zero vacancy rows without fabricating fields
  3. Running ingest twice on the same raw content makes exactly one Claude API call total; the second run reads from the extraction cache
  4. Running ingest twice on the same raw content inserts exactly one vacancy row; the dedup hash prevents double-insertion of normalized duplicate content
**Plans**: 3 plans
- [x] 03-01-PLAN.md — Extraction contract: Zod schema + tool-use JSON Schema, content-hash extraction cache helpers, anthropicModel config field
- [x] 03-02-PLAN.md — Injectable Claude client (forced tool-use) + extractOne: cache-gate → call → Zod-validate → retry-once-then-skip
- [x] 03-03-PLAN.md — Pipeline wiring: pending-raw read/status helpers, deduped vacancy insert, extractPending phase function

### Phase 4: CLI Commands
**Goal**: Users can invoke hire-radar ingest, list, and export from the terminal and receive clean output
**Depends on**: Phase 3
**Requirements**: CLI-01, CLI-02, CLI-03, CLI-04
**Success Criteria** (what must be TRUE):
  1. Running `hire-radar ingest` fetches, extracts, and persists from all sources and prints per-run stats (fetched, extracted, deduped, skipped, Claude API calls)
  2. Running `hire-radar list` with filters (source, keyword/skill, date range, limit) displays matching vacancies in readable terminal output; default limit is 20
  3. Running `hire-radar export` with the same filters dumps a valid JSON array of structured vacancies to stdout
  4. Running a one-time auth command produces a persistent Telegram session string that subsequent ingest runs use without re-authenticating
**Plans**: 5 plans
- [x] 04-01-PLAN.md — queryVacancies: parameterized read-side filter helper (source/keyword/date/limit) powering list + export
- [x] 04-02-PLAN.md — CLI scaffold: bin/hire-radar tsx shim, package.json bin, commander program + four register* command-contract stubs
- [x] 04-03-PLAN.md — list + export commands: aligned table to stdout (default 20, empty→stderr) and pipeable JSON array (no default, []-on-empty)
- [x] 04-04-PLAN.md — ingest command: orchestrator + extractor wiring, --source/--since, per-run stats block, per-source-error exit 0
- [x] 04-05-PLAN.md — auth command: isolated gramjs interactive login, prints persistent session string with store-as-TELEGRAM_SESSION warning
